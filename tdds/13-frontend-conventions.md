# 13 — Frontend Conventions

> Where things live, how they're named, when to extract a component vs. inline it. The goal: any future-me opening this codebase six months from now finds files where they expect them.
>
> Companion to TDD 10 (which covers *what* the frontend does); this doc is *how* it's structured.

## Where each kind of thing goes

### `components/ui/` — primitives

Generated by `pnpm dlx shadcn add <name>`. **Never hand-edit** these files; if you need a variant, compose around them or pass props. If shadcn updates a primitive, regenerate; we don't carry custom diffs in here.

### `components/forms/` — form fields

Thin wrappers binding shadcn primitives to TanStack Form's `useField`. One file per field type:

```
components/forms/
  text-field.tsx       # <TextField name="title" label="Title" />
  textarea-field.tsx
  number-field.tsx
  select-field.tsx     # synchronous options
  combobox-field.tsx   # async-options (artist autocomplete, album autocomplete)
  date-field.tsx
  switch-field.tsx
  form.tsx             # <Form> wrapper providing TanStack Form context + submit handling
  form-error.tsx       # field-level error rendering
```

Forms are **always built from these**, never hand-wired with raw shadcn `<Input>` + manual state. If a form needs a field type that isn't here, add it to `components/forms/` first.

### `components/tables/` — table primitives

```
components/tables/
  data-table.tsx          # <DataTable columns={...} data={...} pagination={...} />
  pagination.tsx          # offset/limit footer
  column-header.tsx       # sortable header w/ TanStack Table
  empty-row.tsx
```

Page-level tables compose these. Column definitions live with the feature, not in `components/tables/`.

### `components/` (root level) — cross-feature shared

Anything used by 2+ features and not a primitive/form/table. Today: `<CoverArt>`, `<EmptyState>`, `<Loading>`. Resist the urge to dump random helpers here.

### `features/<name>/components/` — feature-private

Components used by exactly one feature. The matching detail's candidate row, the wishlist queue's status badge, the library's track-row context-menu — all live under their feature folder. **Don't promote** to `components/` unless a second feature needs it.

### `features/<name>/hooks/` — feature-private hooks

Custom hooks that aren't generated query hooks. Examples: `useMatchQueue()`, `usePlayerKeybindings()`, `useUploadProgress()`.

Generated GraphQL hooks (`useTracksQuery`, `useImportPlaylistMutation`) live in `lib/gql/generated.ts` and are imported directly. Don't re-wrap them per feature unless adding meaningful logic.

### `routes/` — page components

Each route is a thin shell that:
1. Reads search params (typed via TanStack Router).
2. Calls 1–2 query hooks.
3. Composes feature components.

Routes should be ~30–80 lines. If a route file grows past that, the body is begging to be a `features/<name>/components/<page>.tsx`.

## React Query keys

**Single source of truth in `lib/query-keys.ts`**, never inline. Every query key is built by a function with typed args:

```ts
export const queryKeys = {
  tracks: {
    all: ['tracks'] as const,
    list: (filter: TracksFilter) => ['tracks', 'list', filter] as const,
    detail: (id: string) => ['tracks', 'detail', id] as const,
  },
  albums: {
    all: ['albums'] as const,
    list: (filter: AlbumsFilter) => ['albums', 'list', filter] as const,
    detail: (id: string) => ['albums', 'detail', id] as const,
    byArtist: (artistId: string) => ['albums', 'byArtist', artistId] as const,
  },
  // ...
} as const;
```

Why:
- Invalidation: `queryClient.invalidateQueries({ queryKey: queryKeys.tracks.all })` after a mutation that affects any track.
- Hierarchical: invalidating `['tracks']` invalidates `['tracks', 'list', ...]` and `['tracks', 'detail', ...]` together.
- Refactor-safe: rename a key in one place; TS catches every call site.

The graphql-codegen output's `useXxxQuery` hooks accept a `queryKey` override; we always pass one of these registry entries.

### Invalidation rules

| Mutation | Invalidates |
|---|---|
| `createPlaylist` / `renamePlaylist` / `deletePlaylist` | `queryKeys.playlists.all` |
| `addTracksToPlaylist` / `removeTracksFromPlaylist` / `reorderPlaylist` | `queryKeys.playlists.detail(id)` + `queryKeys.playlists.all` (for trackCount) |
| `matchFileToLocalTrack` etc. | `queryKeys.unmatchedFiles.all`, `queryKeys.candidates(fileId)`, `queryKeys.tracks.detail(trackId)` |
| `createWishlistItem` / `retryWishlistItem` / `cancelWishlistItem` | `queryKeys.wishlist.all` |
| `updateUserCreatedTrack` etc. | `queryKeys.tracks.detail(id)`, `queryKeys.tracks.all` |
| `reprocessFile` | `queryKeys.imports.recent`, `queryKeys.files.detail(id)` |

Codify these in a `useInvalidate<MutationName>()` helper if a mutation has many call sites — but only when justified.

### Polling configuration

Per-query, declared in the codegen-generated hook call (or a small wrapper). Defaults from TDD 09 §"Polling cadences":

```ts
useRecentImportsQuery({}, {
  refetchInterval: (data) =>
    data?.recentImports.some(isTransient) ? 2000 : false,
});
```

Polling stops automatically when no rows are in transient states.

## Hooks: where each type lives

| Type | Location |
|---|---|
| GraphQL query / mutation hooks | `lib/gql/generated.ts` (codegen) |
| Cross-feature utility hooks (e.g. `useMediaQuery`) | `lib/hooks/` |
| Feature-specific UI hooks | `features/<name>/hooks/` |
| Player state hook | `features/playback/store.ts` (Zustand selectors) |
| Form bindings | inline in form components — TanStack Form's `useField` doesn't need a wrapper |

## Naming

- Components: `PascalCase`, file matches export (`CoverArt.tsx` exports `CoverArt`).
- Hooks: `useCamelCase`, file matches (`use-match-queue.ts` exports `useMatchQueue`). Prefer kebab-case filenames; React community is split, we pick kebab to match the rust side's snake.
- Types: `PascalCase`, exported from co-located `*.types.ts` only when shared; otherwise inline.
- Constants: `SCREAMING_SNAKE_CASE`.
- Test files: `<name>.test.ts` (Vitest), co-located with the file under test.

## TypeScript conventions

- `strict: true`, `noUncheckedIndexedAccess: true`. No `any`. `unknown` + narrow.
- No barrel files (`index.ts` re-exporting). They wreck tree-shaking and obscure imports. Import directly from the source file.
- No default exports except in `routes/*` files where TanStack Router requires it.
- Discriminated unions for entity-state (`Source: 'MUSIC_BRAINZ' | 'USER_CREATED'` shapes flow through GraphQL types directly).

## Styling

- Tailwind utility classes, composed via the `cn()` helper from `lib/utils.ts`.
- shadcn's CSS variables in `styles/globals.css` for theming. Do not introduce additional CSS files; if you need them, push back and we'll re-evaluate.
- No CSS-in-JS, no styled-components, no Emotion.

## Testing

- Vitest for unit + component tests.
- React Testing Library for components.
- Tests live next to the file (`Component.tsx` + `Component.test.tsx`).
- The matching detail page's match-queue logic gets the most thorough tests (it's the most logic-heavy view); other tests are best-effort.
- No e2e in v2.

## Codegen workflow

- `pnpm graphql-codegen` is run manually after schema changes (and in CI to verify no drift).
- The schema is exported from the rust binary via a build step: `cargo run --bin export-schema > frontend/schema.graphql`. CI runs this and `git diff --exit-code` to ensure committed schema matches what the rust code produces.
- After schema changes: regenerate, fix any TS errors, commit the regenerated `generated.ts` + `schema.graphql` together.

## When to break these rules

- Don't, in v2. The point is consistency.
- If you find a real conflict with these conventions while implementing, update this doc in the same PR rather than working around it silently.
